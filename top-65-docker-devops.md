# Топ-65 вопросов по Docker для DevOps-собеседования

Тот же принцип, что в файлах по Linux, bash и сетям: приоритет по частоте вопросов, подробные ответы с механикой "под капотом", примеры команд.

---

## Уровень 1 — фундамент (1-12)

**1. Что такое Docker и зачем нужен**
Платформа для контейнеризации приложений — упаковывает приложение со всеми зависимостями в единый образ, который одинаково работает на любой машине с Docker. Решает проблему "у меня работает, а на проде нет" за счёт идентичного окружения везде.

**2. Разница между образом и контейнером**
Образ (image) — неизменяемый шаблон: файловая система + метаданные (какие инструкции, entrypoint и т.д.), хранится как набор слоёв. Контейнер — запущенный экземпляр образа: образ + tonкий read-write слой поверх + собственное изолированное пространство процессов/сети. Аналогия: образ — класс, контейнер — объект этого класса.

**3. Архитектура Docker: client, daemon, registry**
Docker client (`docker` CLI) — то, с чем работает пользователь, отправляет команды. Docker daemon (`dockerd`) — фоновый процесс, реально выполняющий работу (сборка образов, запуск контейнеров), слушает Unix-сокет или TCP. Registry — хранилище образов (Docker Hub, приватные registry) — daemon обращается туда за `pull`/`push`.

**4. Что такое Docker Hub**
Публичный registry образов Docker по умолчанию — `docker pull nginx` без указания адреса берёт образ именно оттуда.

**5. Namespaces — изоляция контейнера**
Механизм ядра Linux, дающий процессу изолированное представление о системных ресурсах: PID namespace (свои номера процессов, не видит процессы хоста), network namespace (свой сетевой стек, интерфейсы, таблица маршрутизации), mount namespace (своя файловая система), UTS (свой hostname), IPC (своя межпроцессная коммуникация), user namespace (маппинг UID/GID). Именно namespaces создают ощущение "отдельной машины" внутри контейнера.

**6. Cgroups — зачем нужны**
Control groups — механизм ядра, ограничивающий и учитывающий потребление ресурсов (CPU, память, I/O) группой процессов. Namespaces дают ИЗОЛЯЦИЮ (что видно), cgroups дают ОГРАНИЧЕНИЕ (сколько можно использовать) — вместе они и есть технический фундамент контейнеров, Docker сам ничего "магического" не изобретает, а оркестрирует эти два механизма ядра.

**7. OverlayFS — как хранятся образы**
Union filesystem — объединяет несколько слоёв в единую видимую файловую систему. Каждая инструкция Dockerfile создаёт новый слой (read-only), при запуске контейнера сверху добавляется тонкий read-write слой. При изменении файла из нижнего слоя используется copy-on-write — файл копируется в верхний слой перед изменением, нижний остаётся нетронутым (что позволяет множеству контейнеров шарить одни и те же нижние слои).

**8. VM vs контейнер — ещё раз, подробнее**
VM — гипервизор эмулирует железо, каждая VM грузит полноценное ядро своей ОС — сильная изоляция, но тяжело (гигабайты, минуты старта). Контейнер — все контейнеры на хосте используют ОДНО ядро хоста, изолируясь через namespaces/cgroups — легко (мегабайты, секунды старта), но изоляция принципиально слабее (уязвимость ядра — потенциальный риск для всех контейнеров на нём, это называется "container escape").

**9. Что происходит при `docker run`**
Daemon проверяет, есть ли образ локально (если нет — `pull` из registry) → создаёт новый контейнер (новые namespaces, cgroup, read-write слой поверх образа) → настраивает сеть (по умолчанию подключает к bridge-сети) → запускает процесс, указанный в ENTRYPOINT/CMD, как PID 1 внутри контейнера.

**10. Жизненный цикл контейнера**
`created` (создан, не запущен) → `running` → `paused` (заморожен через cgroup freezer, процессы существуют, но не выполняются) → `exited` (процесс завершился) → можно удалить (`docker rm`) или запустить заново тем же контейнером (`docker start`, в отличие от `docker run`, который всегда создаёт новый).

**11. Docker Engine**
Общее название клиент-серверного приложения Docker целиком: CLI + daemon + API + containerd/runc под капотом.

**12. containerd и runc**
`runc` — низкоуровневая утилита, реально создающая namespaces/cgroups и запускающая процесс контейнера согласно OCI-спецификации (Open Container Initiative — стандарт, чтобы разные инструменты были совместимы). `containerd` — управляет жизненным циклом контейнеров на уровне выше (образы, снапшоты, вызов runc), Docker daemon работает через containerd, а не делает всё сам напрямую — так исторически сложилось после выделения containerd в отдельный CNCF-проект.

## Уровень 2 — Dockerfile (13-28)

**13. Основные инструкции Dockerfile**
`FROM` — базовый образ, `RUN` — выполнить команду при сборке (создаёт слой), `COPY`/`ADD` — скопировать файлы с хоста, `CMD` — команда по умолчанию при запуске контейнера, `ENTRYPOINT` — основная исполняемая программа, `WORKDIR` — рабочая директория, `EXPOSE` — документирует, какой порт слушает приложение (не публикует его сам по себе), `ENV` — переменные окружения, `ARG` — переменные сборки, `USER` — от какого пользователя запускать, `VOLUME` — объявляет точку монтирования.

**14. `COPY` vs `ADD`**
`COPY` — просто копирует файлы/директории с хоста в образ, ничего лишнего. `ADD` умеет то же самое плюс: автоматически распаковывает локальные архивы (`.tar.gz`) и умеет скачивать по URL. Официальная рекомендация Docker — использовать `COPY`, если не нужна именно распаковка архива, потому что поведение `ADD` менее предсказуемо (неявная магия).

**15. `CMD` vs `ENTRYPOINT`**
`CMD` — команда по умолчанию, легко переопределяется при `docker run image другая_команда`. `ENTRYPOINT` — фиксированная основная команда, которую не так просто переопределить (нужен флаг `--entrypoint`). Часто используются вместе: `ENTRYPOINT` задаёт программу, `CMD` — аргументы по умолчанию для неё, которые пользователь может легко заменить своими.
```dockerfile
ENTRYPOINT ["python3", "app.py"]
CMD ["--port", "8000"]
```

**16. Можно ли использовать `CMD` и `ENTRYPOINT` вместе**
Да, и это распространённая практика — см. пример выше. `CMD` в этом случае становится аргументами по умолчанию к `ENTRYPOINT`.

**17. Слои образа и кэширование**
Каждая инструкция — отдельный слой с собственным хэшем. При пересборке Docker сравнивает инструкцию (и для `COPY`/`ADD` — содержимое копируемых файлов) с предыдущей сборкой: если не изменилось — использует кэш, не выполняет заново. Как только один слой инвалидируется — все слои ПОСЛЕ него тоже пересобираются заново, даже если сами не менялись.

**18. Как оптимизировать порядок инструкций для кэша**
Ставить то, что меняется РЕДКО, раньше в файле (установка зависимостей), то, что меняется ЧАСТО — позже (копирование кода приложения). Классическая ошибка — копировать весь код одной командой перед установкой зависимостей, из-за чего любое изменение кода инвалидирует кэш зависимостей.
```dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt      # закэшируется, пока requirements.txt не меняется
COPY . .                                    # меняется часто — ставим позже
```

**19. Multi-stage build**
Dockerfile с несколькими стадиями `FROM`, промежуточные стадии используются только для сборки (например, компиляция с тяжёлыми build-зависимостями), в финальный образ копируется только результат — итоговый образ намного меньше, не содержит компиляторов и промежуточных артефактов.
```dockerfile
FROM golang:1.22 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp

FROM alpine:latest
COPY --from=builder /app/myapp /myapp
ENTRYPOINT ["/myapp"]
```

**20. `.dockerignore`**
Аналог `.gitignore` — исключает файлы/директории из контекста сборки (`node_modules`, `.git`, локальные секреты). Уменьшает размер контекста, отправляемого демону, ускоряет сборку и не даёт случайно затянуть в образ лишнее.

**21. `ARG` vs `ENV`**
`ARG` — переменная, доступная только во время СБОРКИ образа, не сохраняется в финальном образе и не видна в запущенном контейнере. `ENV` — переменная окружения, встраивается в образ и видна и во время сборки, и во время выполнения контейнера.
```dockerfile
ARG VERSION=1.0
ENV APP_VERSION=$VERSION      # можно передать значение ARG в ENV, если нужно сохранить в контейнере
```

**22. На каком этапе выполняются `RUN` vs `CMD`**
`RUN` выполняется во время СБОРКИ образа (`docker build`), результат сохраняется в слое образа. `CMD` не выполняется при сборке — только записывается как метаданные, реально выполняется при СТАРТЕ контейнера (`docker run`).

**23. Как уменьшить размер образа**
Multi-stage build, лёгкий базовый образ (alpine вместо full debian/ubuntu), объединение нескольких `RUN` в один слой (`&&` вместо отдельных инструкций — меньше промежуточных слоёв), очистка кэша пакетного менеджера в том же слое, где он использовался (`apt-get clean` в той же RUN-команде, иначе слой с "мусором" всё равно останется в истории образа), `.dockerignore`.

**24. Alpine vs Debian-based образы**
Alpine — минималистичный дистрибутив (~5МБ база), использует musl libc вместо glibc — образы намного меньше, но иногда возникают проблемы совместимости с бинарниками, скомпилированными под glibc (типичная головная боль с некоторыми Python-пакетами с C-расширениями). Debian-slim — компромисс: заметно легче полного Debian, но остаётся на привычной glibc.

**25. `USER` — зачем не запускать от root**
По умолчанию процессы в контейнере выполняются от root, если явно не указано иное — при компрометации приложения (например, RCE-уязвимость) атакующий получает root ВНУТРИ контейнера, что при определённых конфигурациях (например, примонтированный Docker-сокет) может быть эскалировано до компрометации хоста. Best practice — явно создавать непривилегированного пользователя и переключаться на него.
```dockerfile
RUN useradd -m appuser
USER appuser
```

**26. `HEALTHCHECK`**
Команда, которую Docker периодически выполняет внутри контейнера, чтобы определить, "здоров" ли он, а не просто "процесс всё ещё жив" — контейнер может быть запущен, но приложение внутри — зависшим/неотвечающим.
```dockerfile
HEALTHCHECK --interval=30s --timeout=3s CMD curl -f http://localhost/health || exit 1
```

**27. `ONBUILD`**
Триггер, который срабатывает не при сборке ЭТОГО образа, а при сборке ДРУГОГО образа, использующего этот как базовый (`FROM`). Редкий паттерн на практике, но встречается в некоторых базовых образах — стоит знать, что такая инструкция существует, даже если сам не используешь.

**28. Best practices написания Dockerfile**
Один процесс на контейнер, непривилегированный пользователь, multi-stage build для компилируемых языков, минимизация слоёв и размера образа, конкретные версии базовых образов вместо `latest` (воспроизводимость сборки), `.dockerignore`, кэш-дружественный порядок инструкций, `HEALTHCHECK` для production-образов.

## Уровень 3 — работа с образами и контейнерами (29-40)

**29. `docker build` — основные флаги**
```bash
docker build -t myapp:1.0 .                    # тег и контекст (текущая директория)
docker build --no-cache -t myapp .                # без использования кэша слоёв
docker build -f Dockerfile.prod -t myapp .          # явно указать файл (если не Dockerfile)
docker build --build-arg VERSION=2.0 -t myapp .       # передать ARG
```

**30. `docker tag` — версионирование образов**
Присваивает образу дополнительное имя/версию без пересборки — образы идентифицируются по хэшу содержимого, тег — просто удобная метка поверх.
```bash
docker tag myapp:1.0 myregistry.com/myapp:1.0
docker tag myapp:latest myapp:1.0
```

**31. `docker push`/`docker pull`**
```bash
docker push myregistry.com/myapp:1.0
docker pull nginx:1.25
```

**32. Приватные registry**
Собственный сервер хранения образов вместо публичного Docker Hub — нужен для закрытого/проприетарного кода (актуально, например, для компании вроде UserGate). Варианты: self-hosted (Docker Registry, Harbor), managed (ECR, GitHub Container Registry, Yandex Container Registry).

**33. `docker ps` — флаги**
```bash
docker ps               # только запущенные
docker ps -a              # все, включая остановленные
docker ps -q               # только ID (удобно для скриптов/xargs)
```

**34. `docker exec` vs `docker attach`**
`docker exec` — запускает НОВЫЙ процесс внутри уже работающего контейнера (например, зайти в шелл для отладки), отсоединение не влияет на основной процесс контейнера. `docker attach` — подключается к STDIN/STDOUT/STDERR основного процесса контейнера (PID 1) — выход из attach через Ctrl+C может убить сам контейнер, если не быть осторожным (Ctrl+P Ctrl+Q для безопасного отсоединения).
```bash
docker exec -it mycontainer bash
```

**35. `docker logs` — флаги**
```bash
docker logs mycontainer
docker logs -f mycontainer            # живой просмотр (follow)
docker logs --tail 100 mycontainer      # последние 100 строк
docker logs --since 1h mycontainer       # за последний час
```

**36. `docker inspect`**
Выводит полные метаданные контейнера/образа/сети в JSON — конфигурация сети, volumes, переменные окружения, лимиты ресурсов, статус здоровья и т.д.
```bash
docker inspect mycontainer
docker inspect -f '{{.NetworkSettings.IPAddress}}' mycontainer      # конкретное поле через Go-шаблон
```

**37. `docker stop` vs `docker kill`**
`docker stop` — шлёт `SIGTERM` (даёт время на graceful shutdown), после таймаута (по умолчанию 10 сек) досылает `SIGKILL`, если процесс не завершился сам. `docker kill` — сразу `SIGKILL` (или другой указанный сигнал), без ожидания.

**38. `docker rm`/`docker rmi`**
`docker rm` — удалить контейнер (должен быть остановлен, либо `-f` для принудительного). `docker rmi` — удалить образ (не должно быть контейнеров, использующих его, либо `-f`).

**39. `docker system prune`**
Очищает неиспользуемые ресурсы — по умолчанию остановленные контейнеры, неиспользуемые сети, dangling-образы (без тега). `docker system prune -a` — дополнительно все неиспользуемые образы (не только dangling), `--volumes` — ещё и неиспользуемые volumes (осторожно — необратимо удаляет данные).

**40. `docker stats`**
Живой поток статистики использования ресурсов по каждому контейнеру — CPU%, память, сеть I/O, диск I/O. Полезно для быстрой диагностики "какой контейнер жрёт ресурсы прямо сейчас".
```bash
docker stats
docker stats --no-stream          # один снимок, не живой поток
```

## Уровень 4 — сети и хранилище (41-50)

**41. Docker network drivers**
`bridge` (по умолчанию) — изолированная виртуальная сеть на хосте, контейнеры общаются через неё, наружу — через NAT. `host` — контейнер использует сетевой стек хоста напрямую, без изоляции (быстрее, но менее безопасно). `none` — вообще без сети. `overlay` — сеть, охватывающая НЕСКОЛЬКО хостов (для Swarm/кластерных сценариев).

**42. Как контейнеры находят друг друга по имени**
Docker поднимает встроенный DNS-сервер для пользовательских bridge-сетей (и для docker-compose сетей) — контейнеры в одной сети резолвят друг друга по имени контейнера/сервиса как по hostname, без ручной настройки `/etc/hosts`.

**43. Проброс портов `-p` — как работает под капотом**
Docker добавляет правило DNAT в iptables (в цепочке `DOCKER`), перенаправляющее трафик с указанного порта хоста на внутренний IP и порт контейнера в bridge-сети — то есть проброс порта реализован через тот же механизм NAT, что разбирали в сетевом файле, не какая-то отдельная магия Docker.
```bash
docker run -p 8081:80 nginx      # хост:контейнер
```

**44. Volumes vs bind mounts vs tmpfs**
Volume — управляется Docker, хранится в служебной области (`/var/lib/docker/volumes`), рекомендуемый способ для персистентных данных, независим от структуры файлов хоста. Bind mount — прямая привязка конкретного пути хоста в контейнер, путь контролирует пользователь, удобно для разработки (монтировать локальный код). Tmpfs — хранится только в оперативной памяти хоста, не пишется на диск вообще, исчезает при остановке контейнера — для временных чувствительных данных.

**45. Named volume vs anonymous volume**
Named — создан с явным именем (`docker volume create mydata` или задан в `-v mydata:/path`), легко переиспользовать между контейнерами, легко найти в `docker volume ls`. Anonymous — создаётся автоматически с случайным именем-хэшем, если указать путь без имени слева — легко забыть и превратить в мусор при `docker system prune --volumes`.

**46. Как посмотреть/удалить volumes**
```bash
docker volume ls
docker volume inspect mydata
docker volume rm mydata
docker volume prune          # удалить все неиспользуемые
```

**47. Данные теряются при рестарте — почему и как избежать**
Все изменения в файловой системе контейнера живут в тонком read-write слое ПОВЕРХ образа — при удалении контейнера (`docker rm`) этот слой уничтожается вместе с данными. `docker restart`/`docker stop`+`docker start` данные СОХРАНЯЮТ (тот же контейнер, тот же слой), а вот `docker rm` + новый `docker run` — нет. Решение для персистентности — явно монтировать volume под путь, где приложение хранит данные (например, `/var/lib/postgresql/data` для БД).

**48. Создание собственной сети**
```bash
docker network create mynet
docker run --network mynet --name app1 myimage
docker network connect mynet existing_container      # подключить уже запущенный контейнер
```

**49. `host` network mode — когда используется**
Когда нужна максимальная производительность сети (нет накладных расходов NAT) или когда приложению явно нужен доступ к сетевому стеку хоста напрямую (некоторые сетевые утилиты/мониторинг-агенты). Компромисс — теряется сетевая изоляция контейнера, порты контейнера напрямую занимают порты хоста.

**50. `overlay` network — для чего**
Позволяет контейнерам на РАЗНЫХ физических хостах общаться друг с другом так, будто они в одной локальной сети — используется в Docker Swarm и концептуально похожа на то, как работают сетевые оверлеи в Kubernetes (Calico, Flannel и т.п.), хоть механизм реализации отличается.

## Уровень 5 — Docker Compose (51-56)

**51. Что такое docker-compose и зачем**
Инструмент для описания и запуска многоконтейнерных приложений через один YAML-файл — вместо серии отдельных `docker run` с кучей флагов, один `docker-compose up` поднимает всё окружение целиком с уже настроенной сетью между сервисами.

**52. `depends_on` — что реально гарантирует**
Гарантирует только ПОРЯДОК запуска контейнера (сервис B стартует после того, как контейнер сервиса A запущен), но НЕ гарантирует, что приложение внутри A уже готово принимать соединения (например, PostgreSQL контейнер запущен, но сама СУБД ещё инициализируется несколько секунд). Для реальной готовности нужен `healthcheck` + `condition: service_healthy` в `depends_on`, либо retry-логика в самом приложении.

**53. Переменные окружения в compose**
```yaml
services:
  app:
    environment:
      - DATABASE_URL=postgresql://db:5432/mydb
    env_file:
      - .env
```

**54. Профили (profiles) в docker-compose**
Позволяют помечать сервисы как принадлежащие определённому профилю и запускать только нужное подмножество (`docker-compose --profile debug up`) — удобно, когда есть, например, отладочные сервисы, не нужные в обычном запуске.

**55. `docker-compose up` vs `docker-compose up -d`**
Без `-d` — запуск в foreground, логи всех сервисов сразу в терминал, Ctrl+C останавливает всё. С `-d` (detached) — запуск в фоне, терминал освобождается сразу, логи смотреть отдельно через `docker-compose logs`.

**56. Масштабирование сервиса через compose**
```bash
docker-compose up -d --scale worker=3      # поднять 3 инстанса сервиса worker
```
Требует, чтобы сервис не был жёстко привязан к фиксированному порту хоста (иначе конфликт портов между инстансами) — обычно используется без прямого проброса портов, за балансировщиком.

## Уровень 6 — безопасность, ресурсы, практика (57-65)

**57. Ограничение ресурсов контейнера**
```bash
docker run --memory=512m --cpus=1.5 myapp
```
Реализовано через cgroups — если контейнер превышает лимит памяти, ядро убивает его процесс (OOM kill), а не "плавно тормозит".

**58. Rootless Docker**
Режим, в котором сам Docker daemon и все контейнеры работают без root-прав на хосте — снижает поверхность атаки (даже полный container escape не даёт root на хосте автоматически). Технически сложнее в настройке (некоторые сетевые операции требуют доп. инструментов), но становится стандартом для security-чувствительных окружений.

**59. Docker secrets — зачем лучше, чем env-переменные**
Переменные окружения видны через `docker inspect`, попадают в логи при отладке, видны в `/proc/[pid]/environ` любому процессу с доступом. Docker secrets (в Swarm) монтируются как файлы в `/run/secrets/`, доступны только тем сервисам, которым явно назначены, не хранятся в истории образа/метаданных контейнера.

**60. Сканирование образов на уязвимости**
Инструменты типа `docker scout`, `trivy`, `grype` анализируют слои образа на известные CVE в установленных пакетах/библиотеках — важная часть CI/CD пайплайна перед публикацией образа, особенно в ИБ-ориентированной компании.
```bash
trivy image myapp:1.0
```

**61. Best practices безопасности контейнеров**
Непривилегированный пользователь (не root), минимальный базовый образ (меньше поверхность атаки), read-only файловая система контейнера где возможно (`--read-only`), не монтировать Docker-сокет внутрь контейнера без крайней необходимости (это фактически root на хосте), сканирование образов в CI, конкретные версии образов вместо `latest`, secrets вместо env-переменных для чувствительных данных.

**62. Контейнер падает сразу после старта — диагностика**
```bash
docker logs container_name              # что вывел процесс перед падением
docker inspect container_name             # ExitCode, OOMKilled флаг
docker run -it myimage sh                  # зайти интерактивно, проверить вручную
```
Частые причины: приложение падает с ошибкой сразу (смотреть logs), неверный CMD/ENTRYPOINT, отсутствующая зависимость в образе, контейнер убит по памяти (`OOMKilled: true` в inspect).

**63. Docker Swarm vs Kubernetes — кратко**
Оба — оркестраторы контейнеров. Swarm — встроен в Docker, проще в настройке, меньше возможностей, для небольших/средних кластеров. Kubernetes — отдельная более сложная система, гораздо более широкий набор возможностей (autoscaling, богатая экосистема, декларативные ресурсы), фактический индустриальный стандарт для серьёзной оркестрации сейчас.

**64. `docker-compose logs -f` — практика**
```bash
docker-compose logs -f                  # все сервисы сразу
docker-compose logs -f app db             # только конкретные сервисы
```

**65. Передача данных между контейнерами без сети**
Через общий volume, примонтированный в оба контейнера — один пишет файлы, другой читает их напрямую с диска, без сетевого взаимодействия вообще.
```yaml
services:
  writer:
    volumes:
      - shared_data:/data
  reader:
    volumes:
      - shared_data:/data
volumes:
  shared_data:
```
