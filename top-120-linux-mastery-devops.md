# Топ-120 вопросов Linux — расширенная версия (уверенное владение)

Отличие от `top-100-linux-commands-devops.md`: там — команда за командой, база. Здесь — то, что показывает реальную уверенность в системе: как процессы, память, диски и загрузка устроены изнутри, продвинутые техники, живые сценарии диагностики. Формат тот же: механика + примеры.

## Уровень 1 — процессы и планирование (1-15)

**1. Состояния процесса: R, S, D, T, Z**
`R` (running/runnable) — выполняется или готов к выполнению. `S` (interruptible sleep) — ждёт события, можно разбудить сигналом. `D` (uninterruptible sleep) — обычно ждёт I/O, **нельзя** прервать даже SIGKILL, пока операция не завершится — если процессов в D много и подолгу, это почти всегда означает проблему с диском/NFS, а не с самим процессом. `T` — остановлен (Ctrl+Z или SIGSTOP). `Z` (zombie) — завершился, ждёт reap родителем.
```bash
ps aux | awk '{print $8}' | sort | uniq -c      # сколько процессов в каждом состоянии
```

**2. Процесс vs поток в Linux**
Архитектурно ядро не делает жёсткого различия — оба создаются через `clone()`, разница в том, что расшарено: поток разделяет адресное пространство/файловые дескрипторы с другими потоками того же процесса (флаг `CLONE_VM`), процесс получает собственную копию (copy-on-write при `fork()`).

**3. `fork()` vs `exec()`**
`fork()` создаёт копию текущего процесса (copy-on-write — физически данные не копируются, пока один из процессов их не изменит). `exec()` заменяет код и данные текущего процесса новой программой, PID остаётся тот же. Типичная пара: шелл делает `fork()`, чтобы получить дочерний процесс, затем `exec()` в нём, чтобы запустить введённую команду.

**4. Почему PID 1 особенный**
Первый процесс, запускаемый ядром (init/systemd) — ядро защищает его от обычного `SIGKILL`, он "усыновляет" осиротевшие процессы (reparenting) и обязан корректно обрабатывать сигналы завершения дочерних, иначе накапливаются зомби на всей системе.

**5. Что такое CFS (Completely Fair Scheduler)**
Планировщик CPU по умолчанию для обычных процессов в Linux — распределяет CPU-время пропорционально "весу" процесса (производному от nice-значения), не жёсткими временными слотами, а стремясь дать каждому справедливую долю за период.

**6. `nice` подробнее**
Диапазон -20 (максимальный приоритет) до 19 (минимальный), влияет на вес в CFS, НЕ гарантирует конкретное время выполнения — только относительный приоритет при конкуренции. Отрицательные значения — только root.
```bash
nice -n -5 ./critical_task.sh          # нужен root
renice -n 10 -p 1234                     # изменить приоритет уже запущенного
```

**7. Почему SIGKILL и SIGSTOP нельзя перехватить**
Большинство сигналов процесс может перехватить, заблокировать или проигнорировать через обработчик. `SIGKILL`(9) и `SIGSTOP`(19) — жёстко обрабатываются ядром напрямую, минуя код процесса — гарантия, что систему всегда можно принудительно остановить/убить, даже если процесс написан плохо или враждебен.

**8. Process group и session**
Group объединяет процессы для одновременной доставки сигналов (например Ctrl+C убивает всю foreground-группу разом). Session — уровень выше, обычно привязана к терминалу, содержит одну или несколько групп.

**9. Orphan process — не то же самое, что zombie**
Orphan — процесс, чей родитель завершился раньше него, ядро переприсваивает родителя на init/systemd, дальше живёт нормально. Zombie — уже завершившийся процесс, ждущий, пока родитель заберёт его exit-статус — совсем другая ситуация.

**10. Дерево процессов**
```bash
pstree -p                # с PID
ps auxf                    # тоже дерево, ASCII-графика
```

**11. Кто держит файл открытым**
```bash
lsof /var/log/app.log
fuser /var/log/app.log
```

**12. `ulimit`**
Лимиты ресурсов на процесс: максимум открытых файловых дескрипторов, размер core dump, максимум процессов пользователя. Часто требует явного увеличения для высоконагруженных сервисов (много одновременных соединений = много fd).
```bash
ulimit -n                  # текущий лимит открытых файлов
ulimit -n 65536              # увеличить (в рамках hard limit)
ulimit -a                    # все лимиты разом
```

**13. Context switch**
Переключение CPU между выполнением разных процессов/потоков — дорогая операция (сохранение/восстановление регистров, TLB flush). Аномально высокая частота context switch в `vmstat` — признак перегрузки системы слишком большим числом конкурирующих процессов на малом числе ядер.

**14. Полезное в `/proc/[pid]/`**
`cmdline` — команда запуска, `status` — состояние и память, `fd/` — открытые дескрипторы (символические ссылки на реальные файлы/сокеты), `maps` — карта памяти процесса, `environ` — переменные окружения процесса, `limits` — действующие ulimit.
```bash
cat /proc/1234/status | grep VmRSS       # реальное потребление памяти процессом
ls -la /proc/1234/fd/                       # что именно открыто
```

**15. Сигнал по имени процесса, а не PID**
```bash
pkill -f "python3 app.py"      # по паттерну командной строки
killall nginx                     # по точному имени процесса
```

## Уровень 2 — права доступа и файловая система продвинуто (16-30)

**16. ACL — Access Control List**
Расширенные права сверх стандартного набора owner/group/other — позволяет задать разные права для конкретных ДОПОЛНИТЕЛЬНЫХ пользователей/групп на один файл, не только трёх базовых категорий.
```bash
setfacl -m u:john:rw file.txt        # дать john права rw дополнительно
getfacl file.txt                       # посмотреть все ACL файла
```

**17. `umask`**
Маска, вычитаемая из базовых прав при создании новых файлов (666) и директорий (777). `umask 022` → новые файлы получают 644, директории 755.
```bash
umask               # посмотреть текущую
umask 027             # установить (для текущей сессии)
```

**18. Immutable flag (`chattr +i`)**
Файл нельзя изменить или удалить даже root'ом, пока флаг не снят — используется для защиты критичных конфигов от случайного изменения/удаления.
```bash
chattr +i /etc/critical.conf
lsattr /etc/critical.conf          # посмотреть флаги
```

**19. Что происходит с данными открытого файла после `rm`**
Процесс, уже держащий файл открытым, продолжает иметь к нему доступ даже после `unlink()` — данные физически освобождаются, только когда счётчик ссылок на inode дойдёт до нуля И не останется открытых файловых дескрипторов. Классический сценарий: удалённый лог "продолжает занимать место", пока держащий его процесс не перезапущен.
```bash
lsof +L1          # найти файлы, у которых 0 hard links, но всё ещё открыты процессом
```

**20. Директория всегда имеет минимум 2 hard link**
Сама запись + `.` внутри неё, плюс по одному дополнительному за каждую поддиректорию (её `..` указывает обратно). Поэтому `stat` на пустой директории покажет link count 2, а не 1 — не баг, а особенность структуры файловой системы.

**21. Bind mount**
`mount --bind /src /dst` — примонтировать одну директорию в другое место дерева, тот же контент доступен по двум путям одновременно. Это ровно тот механизм на уровне ОС, на котором построены Docker bind mounts.

**22. Дисковые квоты**
Ограничение места/количества файлов на пользователя или группу на конкретной файловой системе (требует поддержки в fs, ext4 умеет).
```bash
quotacheck -cug /home
edquota username         # интерактивное редактирование лимита
repquota /home             # отчёт по текущему использованию
```

**23. Soft limit vs hard limit**
Soft — предупреждение или временно превышаемая граница (обычно с grace-периодом). Hard — абсолютный предел, превысить нельзя никогда. Применимо и к дисковым квотам, и к `ulimit`.

**24. setuid на практике**
`/usr/bin/passwd` имеет setuid root — обычный пользователь запускает его от своего имени, но во время выполнения процесс получает права root, потому что запись в `/etc/shadow` требует root-доступа, а менять СВОЙ пароль должен уметь любой пользователь.

**25. Journaling файловой системы**
ext4/XFS ведут журнал изменений метаданных ДО их фактического применения к основной структуре — при сбое питания/краше система читает журнал и быстро восстанавливает консистентность вместо полного `fsck` всего раздела, что на больших дисках заняло бы часы.

**26. `fsck`**
Проверка и восстановление целостности файловой системы. Безопасно запускать только на размонтированном (или read-only смонтированном) разделе — на активно используемой ФС может усугубить повреждения.
```bash
fsck -f /dev/sdb1          # принудительная проверка даже "чистого" раздела
```

**27. Квота по inode vs по блокам — разные вещи**
Inode-квота ограничивает КОЛИЧЕСТВО файлов независимо от их размера (актуально при миллионах мелких файлов — можно исчерпать inode при куче свободного места по байтам). Квота блоков ограничивает суммарный ОБЪЁМ данных.

**28. Extended attributes (xattr)**
Метаданные файла сверх стандартных владельца/прав/времени — используются, например, для хранения ACL или SELinux-меток.
```bash
setfattr -n user.comment -v "backup file" file.txt
getfattr -d file.txt
```

**29. Symbolic link vs hard link при копировании инструментами бэкапа**
`cp -a`/`rsync -a` по умолчанию копируют symlink как есть (саму ссылку, не то, на что она указывает) — нужен явный флаг (`-L`/`--copy-links`) для дереференса, если требуется скопировать реальное содержимое цели ссылки.

**30. Разница между `du` с `--apparent-size` и без**
Без флага — реальные блоки на диске (`st_blocks`). С `--apparent-size` — логический размер файла как в `ls -l`, важно для sparse-файлов (файл с "дырами", которые не занимают физическое место, но логически большие — типичный случай для файлов образов дисков).

## Уровень 3 — диски, разделы, LVM, RAID (31-42)

**31. Зачем нужен LVM**
Logical Volume Manager добавляет гибкий слой абстракции между физическими дисками и файловыми системами — можно менять размер логического раздела без изменения физической разметки, объединять несколько дисков в один пул хранения.

**32. Иерархия LVM**
Physical Volume (PV) — физический диск/раздел, подготовленный под LVM. Volume Group (VG) — пул из одного или нескольких PV. Logical Volume (LV) — "виртуальный раздел", нарезанный из VG, на нём уже создаётся файловая система.
```bash
pvcreate /dev/sdb1
vgcreate myvg /dev/sdb1
lvcreate -L 10G -n mylv myvg
```

**33. Расширение LV на лету**
```bash
lvextend -L +5G /dev/myvg/mylv
resize2fs /dev/myvg/mylv          # для ext4
xfs_growfs /mnt/point                # для XFS (только увеличение, не уменьшение)
```

**34. Уровни RAID — практически актуальные**
RAID 0 — striping, скорость, БЕЗ избыточности (отказ одного диска = потеря всех данных). RAID 1 — mirroring, полная избыточность, теряется половина объёма. RAID 5 — striping + распределённая чётность, переживает отказ 1 диска, эффективнее по объёму, чем RAID 1. RAID 10 — комбинация 1+0, быстро и надёжно, но дорого по объёму (нужно вдвое больше дисков).

**35. Программный RAID**
```bash
mdadm --create /dev/md0 --level=1 --raid-devices=2 /dev/sdb1 /dev/sdc1
cat /proc/mdstat          # состояние массива
```

**36. MBR vs GPT**
MBR — до 4 основных разделов, лимит диска 2ТБ, старый стандарт. GPT — до 128 разделов, диски больше 2ТБ, хранит резервную копию таблицы разделов (устойчивее к повреждению) — современный стандарт по умолчанию.

**37. Создание файловой системы**
```bash
mkfs.ext4 /dev/sdb1
mkfs.xfs /dev/sdb1
```

**38. `smartctl` — диагностика здоровья диска**
Читает S.M.A.R.T.-данные напрямую из прошивки диска (предиктивные показатели износа/скорого отказа) — работает на уровне ниже файловой системы.
```bash
smartctl -a /dev/sda          # полный отчёт
smartctl -H /dev/sda           # только общий вердикт здоровья
```

**39. Swap подробнее**
Раздел или файл на диске, используемый как расширение RAM при её нехватке — на порядки медленнее оперативной памяти, активный свопинг (thrashing) — критичное замедление всей системы, не локальная проблема одного процесса.

**40. Создание swap-файла (не раздела)**
```bash
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
```

**41. `df -i` — почему это отдельная метрика от свободного места**
Файловая система может исчерпать inode (лимит на количество файлов) при ещё большом количестве свободных байт — типично при миллионах мелких файлов (например, кэши или сессии). `df -h` в этот момент покажет "полно места", а создание нового файла всё равно упадёт с ошибкой.

**42. LVM snapshot**
Мгновенный снимок состояния LV на конкретный момент времени через copy-on-write — используется для получения консистентного бэкапа "живой" файловой системы без остановки сервисов, использующих её.
```bash
lvcreate -L 1G -s -n mylv_snap /dev/myvg/mylv
```

## Уровень 4 — systemd продвинуто (43-54)

**43. Типы systemd unit-файлов**
`.service` — обычный сервис, `.socket` — активация по сокету (socket activation), `.timer` — замена cron, `.mount` — точка монтирования, `.target` — группа юнитов (аналог runlevel), `.path` — триггер по изменению файла/директории, `.device` — представление устройства.

**44. systemd target vs старые runlevel**
Target — набор юнитов, которые должны быть активны в данном "состоянии" системы (`multi-user.target` ~ runlevel 3, `graphical.target` ~ runlevel 5). В отличие от жёстких числовых runlevel, targets поддерживают гибкие декларативные зависимости и параллельный запуск.

**45. Простой `.service` unit-файл**
```ini
[Unit]
Description=My App
After=network.target

[Service]
ExecStart=/usr/bin/python3 /opt/app/main.py
Restart=on-failure
User=appuser

[Install]
WantedBy=multi-user.target
```

**46. systemd timer vs cron**
Timer — декларативный, логи централизованно через `journalctl`, может зависеть от других юнитов, лучше защищён от параллельного запуска второго экземпляра (если предыдущий ещё не завершился). Cron — проще и привычнее, но менее гибкий, логи разбросаны, не всегда очевидны.

**47. `Restart=` директива**
Политика автоматического перезапуска сервиса при падении: `no` (по умолчанию), `on-failure` (только при ненулевом exit code), `always`, `on-abnormal`. Ключевая часть отказоустойчивости production-сервисов — без неё упавший сервис так и останется лежать.

**48. `systemctl daemon-reload`**
Заставляет systemd перечитать unit-файлы с диска — без этого изменения в файле юнита не подхватятся, даже если сам сервис перезапустить, потому что конфигурация закэширована в памяти демона.

**49. `mask` vs `disable`**
`disable` — убирает из автозапуска, но юнит всё ещё МОЖНО запустить вручную (`systemctl start`). `mask` — создаёт symlink на `/dev/null` вместо unit-файла, юнит физически невозможно запустить даже вручную, пока не размаскирован — используется для жёсткой блокировки конфликтующего сервиса.

**50. Зависимости юнита**
```bash
systemctl list-dependencies nginx
```

**51. `WantedBy` vs `RequiredBy`**
`WantedBy` — "мягкая" зависимость, сбой не блокирует остальную часть target. `RequiredBy` — "жёсткая", сбой зависимости может остановить весь target целиком.

**52. `systemd-analyze`**
Анализ времени загрузки системы.
```bash
systemd-analyze                    # общее время загрузки
systemd-analyze blame                # какие юниты стартуют дольше всего
systemd-analyze critical-chain        # цепочка зависимостей, определяющая общее время
```

**53. Ограничение ресурсов для systemd-сервиса**
```ini
[Service]
MemoryMax=512M
CPUQuota=50%
```
systemd сам настраивает cgroups под капотом — не нужно вручную возиться с файлами cgroup.

**54. Хранение журнала: persistent vs volatile**
По умолчанию журнал может жить только в памяти (исчезает при перезагрузке) — для персистентного хранения на диске нужно явно настроить `Storage=persistent` в `/etc/systemd/journald.conf` (и убедиться, что существует `/var/log/journal`).

## Уровень 5 — память и производительность (55-69)

**55. `buff/cache` в `free` — почему не пугаться маленького "free"**
Linux агрессивно использует "свободную" память под файловый кэш (буферы блочных устройств, кэш страниц файлов) — технически занята, но мгновенно освобождается приложениям по требованию. Важнее смотреть колонку `available`, а не `free`.
```bash
free -h
```

**56. OOM killer**
Механизм ядра, принудительно завершающий процесс при критической нехватке памяти (вместо полного краша системы) — выбирает жертву по эвристике `oom_score` (обычно самый прожорливый непривилегированный процесс).

**57. Как узнать, что процесс убил OOM killer**
```bash
dmesg | grep -i "killed process"
journalctl -k | grep -i oom
```

**58. `oom_score_adj`**
Можно вручную сместить приоритет процесса быть/не быть жертвой OOM killer: `-1000` полностью защищает процесс, `1000` делает первой мишенью.
```bash
echo -500 > /proc/1234/oom_score_adj
```

**59. Page cache vs Swap — разные механизмы**
Page cache — кэш содержимого файлов в оперативной памяти (ускоряет повторное чтение). Swap — выгрузка НЕиспользуемых страниц памяти процессов на диск при нехватке RAM. Разное назначение, часто путают на собеседовании.

**60. Диагностика, что грузит CPU конкретно**
```bash
top / htop                              # общая картина
pidstat 1                                 # per-process статистика по времени
strace -c -p 1234                          # какие именно syscalls делает процесс
```

**61. `perf` — профилировщик уровня ядра**
Показывает, на каких конкретно функциях/инструкциях тратится CPU-время — глубже базового администрирования, но полезно знать, что существует для серьёзной оптимизации производительности.
```bash
perf top                    # живой профиль по системе
perf record -p 1234 -- sleep 10 && perf report
```

**62. Высокий `iowait` в `top`**
CPU простаивает, ожидая завершения операций ввода-вывода — сигнал, что узкое место не вычисления, а диск/сеть, оптимизировать код процессора здесь бессмысленно.

**63. Диск как узкое место — как проверить**
```bash
iostat -x 2
```
Смотреть `%util` (близко к 100% — диск насыщен) и `await` (среднее время ожидания запроса — растёт при перегрузке).

**64. Throughput vs IOPS**
Throughput — объём данных в секунду (МБ/с). IOPS — количество операций в секунду. Для множества мелких файлов важнее IOPS, для больших последовательных передач — throughput. SSD выигрывает у HDD на порядки именно по IOPS, не только по throughput.

**65. Thrashing**
Система тратит больше времени на перекладывание страниц памяти между RAM и swap, чем на полезную работу — критический симптом острой нехватки памяти, требует немедленного вмешательства.

**66. Топ процессов по памяти без `top`**
```bash
ps aux --sort=-%mem | head
```

**67. NUMA — концептуально**
На многосокетных серверах физическая память ближе к одному CPU, чем к другому (Non-Uniform Memory Access) — доступ к "своей" памяти быстрее, чем к памяти другого узла. Продвинутая тема, но полезно знать о существовании для высоконагруженных многоядерных серверов.

**68. `vm.swappiness` — где менять**
```bash
cat /proc/sys/vm/swappiness          # текущее значение, временно до перезагрузки
sysctl vm.swappiness=10                # изменить сейчас
# для постоянного изменения — добавить в /etc/sysctl.conf и sysctl -p
```

**69. cgroups v1 vs v2**
v1 — отдельная иерархия смонтирована для каждого типа ресурса (CPU, память, I/O по отдельности). v2 — единая унифицированная иерархия для всех контроллеров сразу, проще модель — современные дистрибутивы и Docker постепенно перешли на v2 как стандарт.

## Уровень 6 — логи и аудит (70-79)

**70. `/var/log/syslog` vs `journalctl`**
Syslog — классический текстовый лог (демон rsyslog/syslog-ng). journalctl — бинарный структурированный журнал systemd. Многие дистрибутивы используют оба параллельно, journald может пересылать записи в rsyslog для совместимости.

**71. `logrotate`**
Утилита ротации логов по расписанию — предотвращает бесконтрольный рост файлов: переименовывает/сжимает старые, удаляет самые старые сверх заданного количества.
```bash
cat /etc/logrotate.d/nginx          # пример конфига конкретного сервиса
logrotate -d /etc/logrotate.conf      # dry-run, посмотреть что будет сделано
```

**72. Логи за конкретный период в journalctl**
```bash
journalctl --since "2026-07-01" --until "2026-07-02"
journalctl --since "1 hour ago"
```

**73. `journalctl -k`**
Только сообщения ядра — аналог `dmesg`, но через journal с дополнительными возможностями фильтрации.

**74. `journalctl -b`**
Логи с текущей загрузки системы. `-b -1` — предыдущая загрузка, полезно при отладке причины неожиданного ребута.

**75. `auditd`**
Демон аудита безопасности ядра — логирует системные вызовы/события по заданным правилам (кто открыл какой файл, кто выполнил sudo и когда) — особенно актуален для ИБ-ориентированной инфраструктуры.
```bash
ausearch -k identity_changes          # поиск по заданному ключу правила
```

**76. Ротация лога для приложения без встроенной поддержки reopen**
`copytruncate` в logrotate — копирует содержимое файла и обрезает оригинал на месте, не трогая файловый дескриптор приложения — критично для приложений, которые держат файл открытым и не умеют переоткрывать его по сигналу.

**77. `dmesg -T`**
Переводит машинные таймстампы ядра (секунды с момента загрузки) в человекочитаемые календарные даты.

**78. Ограничение размера journal**
```bash
journalctl --vacuum-size=500M          # разовая очистка до заданного размера
```
Постоянно — `SystemMaxUse=` в `/etc/systemd/journald.conf`.

**79. Централизованный сбор логов с нескольких серверов — концептуально**
На одном сервере достаточно `grep`/`journalctl`, но на десятках серверов нужна агрегация — пересылка через rsyslog/Filebeat/Fluent Bit в единое хранилище (ELK/Loki), иначе искать инцидент вручную по каждой машине нереально.

## Уровень 7 — безопасность и hardening (80-91)

**80. `/etc/sudoers` — правильный способ редактирования**
Только через `visudo` — проверяет синтаксис перед сохранением, не даст сохранить битый файл, который заблокирует sudo вообще для всех.
```bash
visudo
```

**81. SSH hardening — основные шаги**
```
PermitRootLogin no
PasswordAuthentication no
Port 2222                    # смена порта — небольшая, но реальная защита от automated-сканеров
```
Плюс: только ключи, `fail2ban` для блокировки после N неудачных попыток.

**82. `fail2ban`**
Мониторит логи (SSH, веб-сервер) на признаки брутфорса, автоматически банит IP через iptables/nftables после превышения порога неудачных попыток за заданное время.

**83. SELinux / AppArmor — концептуально**
Mandatory Access Control поверх обычных unix-прав — даже скомпрометированный процесс с root не может выйти за рамки политики (например, веб-сервер физически не сможет прочитать `/etc/shadow`, даже будучи root, если политика это запрещает). SELinux (RHEL/CentOS/Fedora) — гранулярнее и сложнее. AppArmor (Ubuntu/Debian) — проще, привязан к путям файлов.

**84. DAC vs MAC**
Discretionary Access Control — обычные unix-права, владелец файла сам решает, кому дать доступ. Mandatory Access Control (SELinux/AppArmor) — политика задаётся централизованно администратором и не может быть обойдена даже владельцем файла.

**85. Linux capabilities**
Гранулярная альтернатива модели "либо root, либо ничего" — например `CAP_NET_BIND_SERVICE` разрешает процессу слушать порты <1024 без полного root.
```bash
setcap 'cap_net_bind_service=+ep' /usr/bin/myapp
getcap /usr/bin/myapp
```

**86. `chroot`**
Меняет видимый корень файловой системы для процесса — он "не видит" ничего за пределами указанной директории. Базовая, не абсолютно надёжная изоляция (существуют техники chroot escape) — концептуальный предшественник современных контейнеров.

**87. `chroot` vs полноценный контейнер**
Chroot изолирует только файловую систему (view). Контейнер добавляет namespaces (изоляция процессов/сети) и cgroups (ограничение ресурсов) поверх похожей базовой идеи — принципиально более полная изоляция.

**88. Кто и когда последний раз логинился**
```bash
last              # история входов
lastlog             # последний вход каждого пользователя
```

**89. Поиск потенциально опасных SUID-файлов при аудите**
```bash
find / -perm -4000 -type f 2>/dev/null
```

**90. 2FA для SSH**
Через PAM-модуль (например `google-authenticator`) — требует TOTP-код в дополнение к ключу при подключении, дополнительный уровень поверх обычной SSH-аутентификации.

**91. `iptables` vs `nftables`**
nftables — современный преемник iptables: единый синтаксис для IPv4/IPv6, более эффективная обработка правил в ядре. Большинство актуальных дистрибутивов используют nftables под капотом, даже когда администратор пишет команды в привычном iptables-синтаксисе (через совместимый прокси-слой).

## Уровень 8 — продвинутые shell-техники и однострочники (92-105)

**92. Process substitution**
`<(command)` — подставляет вывод команды туда, где ожидается путь к файлу.
```bash
diff <(sort file1.txt) <(sort file2.txt)
```

**93. Топ-10 самых больших файлов в директории**
```bash
find . -type f -exec du -h {} \; | sort -rh | head -10
du -ah . | sort -rh | head -10
```

**94. Удалить файлы старше N дней одной командой**
```bash
find /tmp -mtime +30 -type f -delete
```

**95. Количество уникальных IP в лог-файле**
```bash
awk '{print $1}' access.log | sort -u | wc -l
```

**96. Топ-10 самых частых IP в access.log**
```bash
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10
```

**97. Живой мониторинг конкретного процесса**
```bash
watch -n 1 'ps aux | grep nginx'
```

**98. Замена текста сразу в нескольких файлах**
```bash
sed -i 's/old/new/g' *.conf
find . -name "*.conf" -exec sed -i 's/old/new/g' {} +      # рекурсивно
```

**99. Проверка синтаксиса bash-скрипта без запуска**
```bash
bash -n script.sh          # только синтаксис
shellcheck script.sh          # полноценный линтер — находит и логические ошибки
```

**100. Безопасный перебор файлов с пробелами в именах**
```bash
find . -name "*.log" -print0 | while IFS= read -r -d '' file; do
    echo "Обработка: $file"
done
```
`-print0` + `-d ''` — null-разделитель, безопасен даже с самыми экзотическими именами файлов (пробелы, переносы строк в имени).

**101. `$()` без кавычек — те же грабли, что с обычными переменными**
Без кавычек результат command substitution тоже проходит через word splitting и globbing.
```bash
files=$(ls *.txt)
for f in $files; do ... done          # ломается на именах с пробелами
```

**102. Комбинация условий в `find`**
```bash
find /var/log -name "*.log" -mtime +7 -a -size +10M      # AND (по умолчанию, -a не обязателен)
find /var/log -name "*.log" -o -name "*.txt"                # OR
```

**103. Построчное сравнение конфигов с контекстом**
```bash
diff -u old.conf new.conf
colordiff -u old.conf new.conf          # то же самое, с подсветкой
```

**104. `xargs -P` — параллельное выполнение**
```bash
find . -name "*.log" | xargs -P 4 -I{} gzip {}
```
Запускает до N процессов одновременно вместо последовательного выполнения — заметно ускоряет массовые операции.

**105. Наблюдение за изменением диска в реальном времени**
```bash
watch -n 1 df -h
```

## Уровень 9 — загрузка, ядро, окружение (106-115)

**106. GRUB**
Загрузчик, показывающий меню выбора ОС/ядра, передаёт управление выбранному ядру с заданными параметрами загрузки.

**107. Параметры загрузки ядра**
```bash
cat /proc/cmdline               # параметры ТЕКУЩЕЙ загрузки
# для изменения на будущее — /etc/default/grub, затем:
update-grub                      # Debian/Ubuntu
```

**108. Модули ядра**
```bash
lsmod                       # загруженные модули
modprobe module_name          # загрузить (с учётом зависимостей)
modprobe -r module_name         # выгрузить
insmod module.ko                # загрузить конкретный файл напрямую (без учёта зависимостей)
```

**109. `sysctl`**
Интерфейс чтения/изменения параметров ядра во время работы без перезагрузки — через `/proc/sys/`.
```bash
sysctl -a | grep swappiness
sysctl vm.swappiness=10          # временно
```

**110. Постоянное изменение sysctl-параметра**
```bash
echo "vm.swappiness=10" >> /etc/sysctl.conf
sysctl -p
```

**111. `/etc/environment` vs `/etc/profile` vs `~/.bashrc`**
`/etc/environment` — системные переменные для всех пользователей/сессий, не shell-специфичный синтаксис (просто `KEY=value`). `/etc/profile`/`~/.bash_profile` — выполняются при LOGIN-сессии. `~/.bashrc` — выполняется при каждом новом interactive non-login shell (например, новое окно терминала внутри уже открытой сессии).

**112. Login shell vs non-login shell**
Login — прямой вход в систему (SSH-сессия, консоль), загружает `/etc/profile` + `~/.bash_profile`. Non-login — например, новое окно терминала в уже открытой GUI-сессии, загружает только `~/.bashrc`.

**113. "Переменная окружения не подхватывается в cron" — причина**
Cron использует минимальное окружение и НЕ читает `~/.bashrc` — переменные нужно либо явно экспортировать внутри самого cron-скрипта, либо задать прямо в crontab.

**114. `initramfs`**
Временная корневая файловая система, загружаемая в память ядром до монтирования реального корня — содержит минимальные драйверы, нужные для доступа к реальному диску (особенно критично для LVM/RAID/шифрованных разделов, где логика монтирования сложнее базовой).

**115. Версия ядра и дистрибутива**
```bash
uname -r                     # версия ядра
cat /etc/os-release             # дистрибутив и версия
```

## Уровень 10 — практические сценарии диагностики (116-120)

**116. "Сервер внезапно затормозил — с чего начнёшь"**
Систематически сверху вниз:
```
uptime                         # load average — общая картина
top / htop                       # что конкретно грузит CPU/память
iostat -x 2                        # диск — не узкое ли место
free -h                              # память/своп
dmesg | tail -50                       # не убил ли что-то OOM killer, ошибки железа
journalctl -p err --since "1 hour ago"   # недавние ошибки в логах
```

**117. "Диск заполнен на 100%, но `du` показывает свободное место"**
Классика: удалённые, но всё ещё открытые файлы каким-то процессом.
```bash
lsof +L1          # находит файлы с 0 hard links, но открытым файловым дескриптором
```
Решение — перезапустить держащий процесс (или дождаться, пока сам закроет дескриптор), место освобождается физически только тогда.

**118. "Не могу подключиться по SSH — порядок диагностики"**
1. `ping host` — сеть в принципе доступна
2. `nc -zv host 22` — порт открыт снаружи
3. На сервере (если есть другой доступ): `systemctl status sshd` — сервис вообще запущен
4. `journalctl -u sshd` / `/var/log/auth.log` — причина отказа (неверный ключ, `PermitRootLogin`, забанен fail2ban'ом)
5. Права на `~/.ssh` — слишком открытые права на `authorized_keys`/приватный ключ, и SSH сам откажется их использовать (это встроенная защита самого SSH, не баг)

**119. "Процесс не реагирует на SIGTERM"**
Проверить состояние в `ps` — если `D` (uninterruptible sleep), процесс ждёт завершения I/O, и НИ `SIGTERM`, НИ даже `SIGKILL` не подействуют мгновенно, пока операция не завершится или не протухнет по таймауту. Понимание этого — сильный сигнал на собеседовании: разница между "не убивается" и "физически не может быть убит прямо сейчас" — не одно и то же.

**120. "Как убедиться, что сервис поднимется сам после ребута"**
```bash
systemctl is-enabled myservice          # проверить автозапуск включён
systemctl enable myservice                 # если нет
```
И в идеале — реально протестировать через `reboot` в некритичном окружении, а не полагаться только на теорию: `is-enabled` говорит о конфигурации, а не гарантирует, что сервис реально успешно стартует при живой перезагрузке (могут быть проблемы с порядком зависимостей, недоступностью сети на момент старта и т.д.).
