# Топ-50 вопросов по BASH-скриптингу для DevOps-собеседования

Отсортировано по приоритету. Это отдельная тема от команд Linux — здесь про сам язык bash: синтаксис, идиомы, типичные ошибки новичков. Именно это имели в виду в требовании "базовый скриптинг на BASH".

---

## Уровень 1 — синтаксис и базовые конструкции (1-15)

**1. Что такое shebang и зачем он нужен**
Первая строка `#!/bin/bash` говорит системе, каким интерпретатором запускать файл при прямом вызове (`./script.sh`). Без shebang нужно явно писать `bash script.sh`.
```bash
#!/bin/bash
echo "Hello"
```

**2. Разница между `sh` и `bash`**
`sh` — исторически POSIX-совместимый шелл (в современных дистрибутивах часто симлинк на `dash`, урезанный и быстрый); `bash` — расширенный шелл с доп. возможностями (массивы, `[[ ]]`, арифметика `(( ))` и т.д.), которых в чистом POSIX sh нет. Скрипт с `#!/bin/sh`, использующий bash-специфичные конструкции, может сломаться на системах, где `/bin/sh` — это dash.

**3. `./script.sh` vs `bash script.sh` vs `source script.sh` — разница**
`./script.sh` — запуск в новом дочернем процессе (нужен `+x` и правильный shebang). `bash script.sh` — явно указываешь интерпретатор, `+x` не обязателен. `source script.sh` (или `. script.sh`) — выполняет команды в ТЕКУЩЕМ шелле, а не в дочернем процессе — поэтому переменные/функции из скрипта остаются доступны после его завершения (используется для конфигов типа `.bashrc`).

**4. Как сделать скрипт исполняемым**
```bash
chmod +x script.sh
./script.sh
```

**5. Объявление и использование переменных**
Без пробелов вокруг `=`, обращение через `$` или `${}`.
```bash
NAME="Imeon"
echo $NAME
echo ${NAME}       # фигурные скобки — явная граница имени переменной
```

**6. `local` vs глобальная переменная в функции**
Без `local` переменная, созданная внутри функции, становится глобальной для всего скрипта — частый источник багов.
```bash
counter=0
increment() {
    local counter=0      # локальная копия, не трогает внешнюю
    counter=$((counter + 1))
}
```

**7. `export` — зачем нужен**
Без `export` переменная видна только текущему шеллу; с `export` — передаётся во все дочерние процессы (например, в скрипт, который вызывается из текущего).
```bash
export DATABASE_URL="postgresql://localhost/db"
python3 app.py         # увидит DATABASE_URL в своём окружении
```

**8. Позиционные параметры: `$1 $2 $@ $* $# $0`**
`$0` — имя самого скрипта, `$1`, `$2`... — переданные аргументы по порядку, `$#` — их количество, `$@`/`$*` — все аргументы сразу.
```bash
#!/bin/bash
echo "Script: $0, first arg: $1, total args: $#"
```

**9. Разница между `$@` и `$*`**
Без кавычек — ведут себя одинаково. В кавычках `"$@"` разворачивается в отдельные слова (каждый аргумент — свой элемент, сохраняются пробелы внутри аргументов), `"$*"` — в ОДНУ строку через первый символ `$IFS`. На практике `"$@"` — почти всегда правильный выбор при переборе аргументов.
```bash
for arg in "$@"; do echo "$arg"; done      # правильно — каждый аргумент отдельно
```

**10. `$?` — код завершения последней команды**
0 — успех, любое другое число — ошибка.
```bash
grep "pattern" file.txt
if [ $? -eq 0 ]; then
    echo "Найдено"
fi
```

**11. Условные конструкции `if/elif/else`**
```bash
if [ "$1" == "start" ]; then
    echo "Запуск"
elif [ "$1" == "stop" ]; then
    echo "Остановка"
else
    echo "Неизвестная команда"
fi
```

**12. Разница между `[ ]` и `[[ ]]`**
`[ ]` — POSIX-совместимый тест (алиас команды `test`), требует кавычек вокруг переменных для безопасности, не понимает `&&`/`||` напрямую внутри. `[[ ]]` — bash-расширение, безопаснее с пустыми/спецсимвольными переменными, поддерживает `&&`, `||`, `=~` для regex-сравнения. В современном bash-коде почти всегда предпочтительнее `[[ ]]`.
```bash
[[ -f "$file" && -r "$file" ]]        # работает без доп. скобок
```

**13. Операторы теста: `-f -d -e -z -n -eq -gt -lt`**
`-f` файл существует, `-d` директория существует, `-e` существует (любой тип), `-z` строка пустая, `-n` строка непустая, `-eq/-ne/-gt/-lt/-ge/-le` — числовое сравнение (не `==`/`<`/`>` — те для строк или требуют `[[ ]]`).
```bash
[ -f "/etc/passwd" ] && echo "файл существует"
[ -z "$VAR" ] && echo "переменная пустая"
```

**14. Арифметика: `(( ))`, `let`, `$(( ))`**
```bash
count=5
((count++))                    # инкремент
result=$((count * 2))            # арифметическое выражение
let "count = count + 1"           # альтернативный синтаксис
```

**15. Циклы `for`, `while`, `until`**
```bash
for i in 1 2 3; do echo "$i"; done
for ((i=0; i<5; i++)); do echo "$i"; done      # C-подобный синтаксис
while [ "$attempts" -lt 5 ]; do ((attempts++)); done
until [ -f "/tmp/ready" ]; do sleep 1; done      # выполняется, пока условие ЛОЖНО
```

## Уровень 2 — ввод-вывод, кавычки, подстановки (16-30)

**16. `break` и `continue`**
```bash
for i in 1 2 3 4 5; do
    [ "$i" -eq 3 ] && continue      # пропустить итерацию
    [ "$i" -eq 5 ] && break          # выйти из цикла
    echo "$i"
done
```

**17. `case/esac`**
Удобнее множественного `if/elif` при сравнении одной переменной со множеством значений.
```bash
case "$1" in
    start) echo "Запуск";;
    stop)  echo "Остановка";;
    *)     echo "Неизвестно";;
esac
```

**18. Функции: объявление и возврат значения**
`return` возвращает только код завершения (0-255), для возврата "данных" используют `echo` + command substitution.
```bash
get_status() {
    echo "active"          # это "возвращаемое значение"
    return 0                 # это код завершения функции
}
result=$(get_status)
```

**19. Массивы: индексные и ассоциативные**
```bash
arr=("one" "two" "three")
echo "${arr[1]}"                # two
echo "${#arr[@]}"                # длина массива — 3
declare -A map
map["key"]="value"
echo "${map[key]}"
```

**20. Строковые операции**
```bash
str="Hello World"
echo "${#str}"                  # длина строки
echo "${str:0:5}"                 # подстрока — "Hello"
echo "${str/World/Bash}"           # замена первого вхождения
```

**21. Command substitution: `$()` vs backticks**
Оба выполняют команду и подставляют вывод, но `$()` предпочтительнее — читаемее и корректно вкладывается друг в друга (`` `` `` `` `` — сложно и легко ошибиться, `$(  $( )  )` — прозрачно).
```bash
current_date=$(date +%Y-%m-%d)
files=$(ls /tmp | wc -l)
```

**22. Одинарные vs двойные кавычки**
Одинарные `'...'` — буквально всё, без подстановок и раскрытия переменных. Двойные `"..."` — переменные (`$VAR`) и command substitution (`$()`) раскрываются, спецсимволы (кроме `$`, `` ` ``, `"`, `\`) — нет.
```bash
name="Imeon"
echo '$name'          # выведет буквально: $name
echo "$name"           # выведет: Imeon
```

**23. Зачем кавычки вокруг переменных ($VAR vs "$VAR") — word splitting и глоббинг**
Без кавычек значение переменной проходит через word splitting (разбивается по `$IFS`, обычно пробелам) и глоббинг (`*` разворачивается как маска файлов) — классический источник багов при путях с пробелами.
```bash
file="my file.txt"
rm $file            # ОШИБКА: попытается удалить "my" и "file.txt" как два файла
rm "$file"            # правильно — один файл с пробелом в имени
```

**24. Heredoc `<<` и herestring `<<<`**
Heredoc — многострочный блок текста как ввод для команды. Herestring — одна строка/переменная как ввод.
```bash
cat << EOF
Строка 1
Строка 2
EOF

grep "pattern" <<< "$variable"
```

**25. Перенаправление ввода-вывода**
```bash
command > file.txt          # stdout в файл (перезапись)
command >> file.txt          # stdout в файл (дозапись)
command < file.txt            # файл как stdin
command 2> errors.log          # только stderr
command > out.log 2>&1          # stdout и stderr вместе
command &> all.log               # то же самое короче
```

**26. Пайпы `|` — отличие от перенаправления**
Перенаправление связывает команду с файлом, пайп связывает stdout одной команды со stdin другой — данные текут между процессами без промежуточного файла.
```bash
ps aux | grep nginx | awk '{print $2}'
```

**27. `&&` и `||` в командной строке**
`&&` — выполнить следующую команду, только если предыдущая завершилась успешно (код 0). `||` — только если предыдущая упала.
```bash
mkdir /tmp/build && cd /tmp/build          # cd только если mkdir успешен
ping -c1 host || echo "хост недоступен"
```

**28. `read` — чтение ввода**
```bash
read -p "Введите имя: " name
echo "Привет, $name"
```

**29. Построчное чтение файла: `while read line`**
```bash
while IFS= read -r line; do
    echo "Строка: $line"
done < file.txt
```
`IFS=` — не обрезать ведущие/конечные пробелы строки. `-r` — не интерпретировать обратные слэши как escape-последовательности (иначе `\n` в данных сломает чтение). Частая ошибка новичков — забыть оба флага.

**30. `getopts` — обработка аргументов командной строки скрипта**
```bash
while getopts "f:v" opt; do
    case $opt in
        f) filename="$OPTARG";;
        v) verbose=true;;
    esac
done
# использование: ./script.sh -f myfile.txt -v
```

## Уровень 3 — надёжность, обработка ошибок, отладка (31-40)

**31. `set -e` — зачем нужен**
По умолчанию bash-скрипт продолжает выполнение даже после команды с ненулевым кодом возврата — это опасно в production-скриптах. `set -e` останавливает скрипт при первой же ошибке.
```bash
#!/bin/bash
set -e
cp important_file.txt /backup/    # если упадёт — скрипт остановится, не пойдёт дальше
rm important_file.txt
```

**32. `set -u` — зачем нужен**
Ошибка при обращении к необъявленной переменной вместо тихой подстановки пустой строки — ловит опечатки в именах переменных.
```bash
set -u
echo "$UNDEFINED_VAR"     # с set -u — ошибка и остановка, без — просто пустая строка
```

**33. `set -o pipefail` — зачем нужен**
Без него код возврата пайпа — это код возврата ПОСЛЕДНЕЙ команды в цепочке, даже если команда раньше в пайпе упала. `pipefail` делает весь пайп "упавшим", если упала любая его часть.
```bash
set -o pipefail
false | true          # без pipefail код возврата 0 (успех), с pipefail — 1 (ошибка)
```
Хороший тон в продакшн-скриптах — писать все три флага вместе: `set -euo pipefail`.

**34. `trap` — обработка сигналов в скрипте**
Перехватывает сигналы (или выход из скрипта) и выполняет заданное действие — полезно для очистки временных файлов при прерывании.
```bash
trap 'rm -f /tmp/lockfile; echo "Прервано"' EXIT SIGINT SIGTERM
touch /tmp/lockfile
sleep 100      # если прервать Ctrl+C — lockfile всё равно удалится
```

**35. Как задать и проверить exit code**
```bash
exit 0          # успех
exit 1           # общая ошибка
exit 2            # обычно "неверное использование" по соглашению
# проверка:
some_command
echo "Код возврата: $?"
```

**36. `==` vs `=` в тестах**
Внутри `[[ ]]` — оба работают одинаково для строк. Внутри `[ ]` (POSIX test) — строго `=`, `==` не всегда переносимо. Частая путаница: `=`/`==` — сравнение строк, `-eq` — сравнение чисел; `"5" == "5.0"` как строки не равны, а как числа `-eq` были бы равны.

**37. Проверка, что переменная пустая или не задана**
```bash
if [ -z "$VAR" ]; then echo "пусто или не задано"; fi
if [ -n "${VAR+x}" ]; then echo "переменная задана (даже если пустая строка)"; fi
```

**38. Значения по умолчанию: `${VAR:-default}`**
```bash
NAME=${NAME:-"default_name"}          # если NAME не задан — используется default
PORT=${PORT:-8080}
${VAR:=default}                          # то же, но ЕЩЁ И присваивает VAR это значение
```

**39. Подстановки с обрезкой/заменой: `${VAR#pattern}`, `${VAR%pattern}`, `${VAR/old/new}`**
```bash
path="/var/log/app.log"
echo "${path##*/}"           # app.log — убрать всё до последнего /
echo "${path%.log}"            # /var/log/app — убрать .log с конца
echo "${path/log/LOG}"          # заменить первое вхождение "log"
```

**40. Отладка скриптов: `bash -x`, `set -x`**
Печатает каждую выполняемую команду с подставленными значениями переменных перед её исполнением — самый быстрый способ понять, что скрипт реально делает.
```bash
bash -x script.sh
# или внутри скрипта:
set -x        # включить трассировку с этого места
...
set +x         # выключить
```

## Уровень 4 — продвинутое и частые ошибки (41-50)

**41. Subshell `( )` — что это**
Команды в круглых скобках выполняются в отдельном дочернем процессе — переменные, изменённые внутри, не видны снаружи после завершения.
```bash
(cd /tmp && rm *.tmp)      # cd действует только внутри subshell, текущая директория снаружи не меняется
```

**42. Subshell `( )` vs group `{ }`**
`( )` — отдельный процесс (изоляция переменных/cd), `{ }` — просто группировка команд в ТЕКУЩЕМ шелле (обязательны пробелы после `{` и `;` перед `}`).
```bash
{ echo "a"; echo "b"; } > output.txt      # group — быстрее, без форка процесса
```

**43. Почему переменные не передаются в фоновый процесс/subshell без export**
Дочерний процесс получает копию окружения родителя в момент запуска — если переменная не была `export`, она просто не существует в окружении, которое видит дочерний процесс.
```bash
VAR="test"
bash -c 'echo $VAR'        # выведет пустую строку
export VAR="test"
bash -c 'echo $VAR'        # выведет: test
```

**44. `source`/`.` — зачем и чем отличается от обычного запуска**
Выполняет скрипт в текущем шелле (не создаёт дочерний процесс) — поэтому переменные, функции, `cd` из "сорсенного" скрипта остаются в текущей сессии. Именно так подключают `.bashrc`, конфиги, вспомогательные функции.
```bash
source ./config.sh          # или: . ./config.sh
```

**45. Особенности bash-скриптов в cron**
У cron минимальный `$PATH` (часто только `/usr/bin:/bin`) и нет интерактивного окружения (`~/.bashrc` не подгружается) — скрипт, который отлично работает в терминале, может падать в cron из-за недоступной команды или переменной. Правило: в cron-скриптах использовать абсолютные пути к командам или явно задавать `PATH` в начале скрипта.
```bash
# в crontab -e:
* * * * * /usr/bin/bash /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```

**46. Идемпотентность bash-скриптов**
Повторный запуск скрипта не должен ломать систему или дублировать результат — перед действием проверять текущее состояние.
```bash
if [ ! -d "/opt/app" ]; then
    mkdir -p /opt/app          # создать, только если ещё нет
fi
# или короче:
mkdir -p /opt/app          # mkdir -p сам по себе идемпотентен — не упадёт, если директория уже есть
```

**47. Логирование и обработка ошибок — хороший тон**
```bash
log() { echo "$(date '+%Y-%m-%d %H:%M:%S') $1" >> /var/log/myscript.log; }

if ! cp file.txt /backup/; then
    log "ERROR: не удалось скопировать файл"
    exit 1
fi
log "Бэкап выполнен успешно"
```

**48. Частая ошибка: незакавыченные переменные**
```bash
if [ $var == "test" ]; then       # упадёт с ошибкой, если $var пустой ("[ == test ]" — синтаксическая ошибка)
if [ "$var" == "test" ]; then      # правильно
```

**49. Частая ошибка: сравнение чисел как строк или наоборот**
```bash
[ "10" -gt "9" ]        # true — числовое сравнение, правильно для чисел
[ "10" \> "9" ]           # false — строковое сравнение ("1" < "9" лексикографически)
```

**50. Частая ошибка: лишние/недостающие пробелы в `[ ]`**
`[` — это на самом деле команда (алиас `test`), ей нужны пробелы вокруг аргументов как любой команде.
```bash
[ "$a" == "$b" ]      # правильно — пробелы вокруг [ и перед ]
["$a"=="$b"]            # ОШИБКА: command not found — воспринимается как имя команды "[$a"
```

## Практическое задание напоследок (частый формат на живом собеседовании)

Попроси написать вживую что-то в духе: "скрипт, который проверяет каждые N секунд, жив ли процесс, и перезапускает его, если нет" или "скрипт бэкапа с ротацией" — оба разобраны с готовым кодом в файле `usergate-devops-interview-prep.md`, раздел 5. Если дадут задачу "с нуля" — держи в голове микро-чеклист: shebang → `set -euo pipefail` → кавычки вокруг переменных → проверка идемпотентности → логирование ошибок. Даже если не успеешь всё — то, что проговоришь этот чеклист вслух, уже показывает, что думаешь как инженер, а не как человек, который просто помнит синтаксис.
