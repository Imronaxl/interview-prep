# Linux Mastery Game — архитектура и дизайн

Интерактивная веб-игра для прокачки Linux до уровня уверенного профессионального владения. Без профилей/аккаунтов — локальный тренажёр с сохранением прогресса в браузере. Контент — производный от уже собранных справочников (`top-100-linux-commands-devops.md`, `top-120-linux-mastery-devops.md`), не выдумывается заново.

---

## 1. Концепция и педагогика

Два режима обучения, каждый честно ограничен тем, что реально можно сделать хорошо:

**Terminal Practice** — настоящий интерактивный терминал (xterm.js) поверх симулированной виртуальной Linux-среды (файловая система, процессы, права доступа). Даётся сценарий с целью, ты вводишь реальные команды, среда честно реагирует так, как отреагировала бы настоящая система — навигация, права, текстовые утилиты, базовое управление процессами. Это то, что реально можно надёжно симулировать в браузере без бэкенда.

**Theory Mode** — флэшкарты/квизы для того, что **невозможно честно симулировать в браузере** (LVM, RAID, systemd internals, boot process, память ядра, OOM killer) — вместо фальшивой имитации того, что не может быть настоящим, для этих тем используется прямой вопрос-ответ с объяснением механизма, взятый из справочников.

Разделение режимов — осознанное архитектурное решение, а не недоработка: лучше честно сказать "это квиз, не терминал", чем сделать бутафорскую имитацию LVM, которая учит неправильным рефлексам.

**Прогрессия:** модули organized по тем же тирам, что в справочниках (файлы/права → процессы → текст → диски → systemd → сети → безопасность → продвинутые сценарии), внутри каждого — уровни по возрастанию сложности. Открытие следующего модуля не блокируется жёстко предыдущим (свободная навигация), но дефолтный путь — по порядку.

**Обратная связь:** мгновенная проверка после каждой введённой команды в terminal-режиме (не только по кнопке "проверить"), прогрессивные подсказки (намёк → более конкретная подсказка → показать ответ, с штрафом к XP за каждый уровень подсказки), объяснение "почему это работает именно так" после прохождения каждого уровня — не просто "верно/неверно".

**Геймификация:** XP за уровни (меньше XP, если использовались подсказки), streak (дни подряд с практикой), "confidence meter" по каждому модулю — не абстрактный процент прохождения, а метрика, снижающаяся со временем без повторения (лёгкий spaced repetition — модуль, который давно не трогали, помечается как "стоит освежить").

## 2. Технический стек

- **Frontend:** React + Vite (чистый SPA, без необходимости в SSR/бэкенде — соответствует требованию "без профиля")
- **Терминал:** `xterm.js` — тот же терминальный эмулятор, что используется в VS Code, полностью полирован из коробки (курсор, история, цвета, resize)
- **Стилизация:** Tailwind CSS + компоненты в духе shadcn/ui — современный, чистый вид, не generic-bootstrap
- **Состояние:** Zustand (лёгкий, без boilerplate Redux, достаточно для объёма состояния этого приложения)
- **Персистентность:** только `localStorage`/`IndexedDB` — никакого бэкенда, никакой авторизации, весь прогресс живёт в браузере пользователя
- **Контент:** JSON-файлы (уровни, квизы) — генерируются/пишутся на основе reference `.md` файлов, а не хранятся в БД

## 3. Виртуальная Linux-среда — ядро всего проекта

Это самая важная и самая сложная часть — от её качества зависит, насколько честным будет "запуск команд".

### 3.1 Виртуальная файловая система

Дерево объектов в памяти (персистится в localStorage между сессиями конкретного уровня, если нужно):
```typescript
interface VNode {
  type: 'file' | 'directory' | 'symlink';
  name: string;
  permissions: string;        // "rwxr-xr-x"
  owner: string;
  group: string;
  size: number;
  mtime: Date;
  content?: string;             // для файлов
  children?: Record<string, VNode>;  // для директорий
  linkTarget?: string;            // для symlink
}
```

### 3.2 Интерпретатор команд

Парсер должен честно поддерживать (это не опционально, это то, что делает практику реальной, а не игрушечной):
- Пайпы: `cmd1 | cmd2 | cmd3`
- Редиректы: `>`, `>>`, `<`, `2>`, `2>&1`
- Логические операторы: `&&`, `||`
- Переменные и подстановки: `$VAR`, `$(command)`
- Глоббинг: `*.log`, `file?.txt`

### 3.3 Набор симулируемых команд (MVP-приоритет)

Реализовать реалистично, с настоящими флагами и поведением (не заглушки): `ls`, `cd`, `pwd`, `cat`, `echo`, `mkdir`, `touch`, `rm`, `cp`, `mv`, `chmod`, `chown`, `grep`, `find`, `head`, `tail`, `wc`, `sort`, `uniq`, `cut`, `awk` (базовые паттерны `{print $N}`), `sed` (базовая `s///`), `ps` (над фейковой таблицей процессов), `kill`, `df`, `du`, `ln`, `stat`, `file`, `less`/`more` (упрощённо), `whoami`, `id`, `date`, `history`.

Команды, которые НЕ пытаемся честно симулировать (уходят в Theory Mode): `systemctl`, `mount`, `lvcreate`, `mdadm`, `iptables`, всё, что требует реального ядра/железа.

### 3.4 Фейковая таблица процессов

Для сценариев на `ps`/`kill`/`top` — заранее заданный правдоподобный список процессов на уровень (PID, имя, CPU%, MEM%, состояние), не настоящие процессы браузера — так `kill -9 1234` в сценарии "завис nginx" может честно "убить" процесс в виртуальной таблице и изменить вывод последующего `ps`.

### 4.3 Модули (структура контента верхнего уровня)

1. Файлы и права доступа
2. Процессы и планирование
3. Текстовые утилиты и пайплайны
4. Диски и хранилище (частично terminal, частично theory — LVM/RAID уходят в theory)
5. systemd и сервисы (в основном theory — systemctl нельзя честно симулировать глубоко)
6. Сети — базовые команды (ping/curl с замоканными правдоподобными ответами)
7. Безопасность и hardening (в основном theory)
8. Продвинутые сценарии диагностики (комбинированные terminal-уровни, воспроизводящие сценарии 116-120 из справочника — "сервер тормозит", "диск полон, а du показывает свободное место")

## 6. Режимы игры

- **Обычный режим** — прохождение уровня без ограничения по времени, полный доступ к подсказкам
- **Speedrun-режим** — таймер на решение, без подсказок, для тренировки той самой уверенности на очном собеседовании, где нужно печатать без раздумий
- **Review-режим** — теоретические квизы по темам с низким confidence meter (spaced repetition), запускается с главного экрана как отдельная кнопка "освежить слабые места"

## 7. Источник истины по контенту

Весь контент уровней/квизов должен происходить из уже написанных справочников, не изобретаться заново:
- `top-100-linux-commands-devops.md` → terminal-уровни модулей 1-3, 6
- `top-120-linux-mastery-devops.md` → theory-квизы модулей 2, 4, 5, 7, 8, и terminal-сценарии модуля 8 (116-120 — готовые сценарии диагностики, почти дословно переносятся в формат terminal-уровня)
- `top-50-bash-scripting-devops.md` → отдельный будущий модуль (не в MVP, см. план фаз)

`relatedReference`/`sourceReference` в каждом уровне/вопросе должны указывать на конкретный номер вопроса в исходном справочнике — это не просто для порядка, а чтобы при желании можно было провалиться в более глубокое объяснение оригинального файла.
